# 实验扩展：客服中心与真实大模型接口集成（2026-10-20）

## 1. 新需求

- U1 居民/商户可创建客服工单，输入分类、主题与正文，查看其工单状态和聊天历史，提交补充消息。
- U2 管理员作为人工客服，可查看所有工单、回复咨询、将工单标记为待处理/处理中/已解决。
- U3 每个工单具有独立权限边界；普通用户不能读取或回复其他用户的工单。
- U4 已登录用户可向配置的真实大模型询问出行及积分规则；未配置 Key 时必须明确禁用 AI 对话，提供不冒充 AI 的本地 FAQ。
- U5 严禁在前端传递服务商密钥，模型回答不可修改积分/订单/清算状态。

## 2. 持久化模型与迁移策略

- `support_tickets(id, user_id, category, subject, status, created_at, updated_at)`：一名用户拥有多张工单。
- `support_messages(id, ticket_id, sender_id, content, created_at)`：工单1:N对话，成员或管理员追加。
- ORM 通过 `Base.metadata.create_all` 在已有 SQLite DB 上**新增表，不删改**原行程、积分和订单数据。课程演示采用该策略；真实生产系统建议采用 Alembic 迁移和数据备份。
- `SupportTicket` 采用 `OPEN → IN_PROGRESS → RESOLVED`，用户再次回复会设回 `OPEN`。

## 3. API 与 RBAC

| HTTP API | 权限 | 功能 |
|---|---|---|
| `GET /api/support/tickets` | 登录用户 | 用户仅本人；管理员全部 |
| `POST /api/support/tickets` | 居民/商户 | 新建工单与首条留言（201） |
| `GET /api/support/tickets/{id}` | 所有者/管理员 | 读取工单与最多200条消息 |
| `POST /api/support/tickets/{id}/messages` | 所有者/管理员 | 回复消息、更新状态 |
| `PATCH /api/support/tickets/{id}/status` | 管理员 | 设置处理状态 |
| `GET /api/assistant/config` | 登录用户 | 返回是否配置及模型名，不包含 Key |
| `POST /api/assistant/chat` | 登录用户 | 使用外部兼容 API 获取真实模型回复 |

## 4. AI 技术方案

请求链：浏览器用户主动输入 → JWT 鉴权、Pydantic 输入限长 → 服务端 System Prompt + 最近8条历史消息 → httpx HTTPS POST `/chat/completions` → 返回答复。服务端环境变量 `AI_API_KEY`、`AI_MODEL`、`AI_BASE_URL`；错误信息不回显下游的任何原始响应正文。AI聊天历史仅保存于前端内存，不落盘。无 Key 时HTTP 503和禁用按钮；右侧 FAQ 为**确定性的非 AI 内容**。

System Prompt 包含演示碳核算参数、功能边界、禁止伪造账户与核证数据、敏感信息提醒。模型可能产生幻觉，因此无权直接写积分/清算表。

## 5. 测试及证据

- 原19项测试通过。
- 新增8个自动测试：客服创建/三方回复/关闭再打开、RBAC与信息隔离、字段校验、无模型配置提示、模拟真实请求结构与秘钥不泄露、下游认证失败脱敏、危险URL拒绝、UI静态资源。
- 共27项 `pytest` 测试通过；Chromium页面模拟接口交互测试验证居民工单/管理员客服及AI接入状态，JS错误数0。
- 未连接任何真实收费模型的Key；模型网络成功依赖使用者自行配置真实凭据及账户额度，不能将模拟供应商测试当作真实推理证明。

## 6. 面向答辩的问题

1. 为什么AI不直接管理积分？答：积分需要确定性规则、事务一致性与审计，模型仅承担自然语言问答。
2. 为什么客服必须保存数据库？答：跨用户登录及管理员登录需保留工单、消息与状态变更。
3. 如何防止越权？答：所有客服API按JWT用户和工单 `user_id` 进行资源级权限检查，管理员是例外。
4. 为什么需要独立AI配置？答：服务端Key隔离、防止在浏览器源码中泄露，允许更换兼容模型提供商。
5. 使用 AI 的环节和人工验证？答：初稿辅助实现并人工审查，pytest与Chromium mock交互已执行；真正联通收费模型仍需使用者配置验证，如实记录而非宣称已完成。
